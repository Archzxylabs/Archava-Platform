### Exact API mapping

**Endpoint.** `POST https://api.postmarkapp.com/email/withTemplate` — the documented "Send email with template" endpoint. This is the only URL the package contains (`POSTMARK_SEND_URL`).

**Request.** Headers exactly: `accept: application/json`, `content-type: application/json`, `x-postmark-server-token: <injected token>`. Header names are the lower-case spelling so a fake transport and a server compare one shape. Body fields, and only these:

| Field                      | Source                                 | Note                                                                                              |
| -------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `To`                       | `request.recipient`                    | one address, never a comma-joined list                                                            |
| `From`                     | `request.template.senderAddress`       | read back off the resolved template, never off the request                                        |
| `TemplateId`               | `request.template.providerTemplateId`  | sent as an **integer** when the string is all digits                                              |
| `TemplateAlias`            | `request.template.providerTemplateId`  | sent as the **alias** instead, exactly one of the two                                             |
| `TemplateModel`            | fixed `{}`                             | required by the endpoint; empty because every rendered value comes from the tenant's own template |
| `MessageStream`            | constructor option, default `outbound` | documented default                                                                                |
| `Metadata.archava_attempt` | derived label                          | this package's own opaque attempt label                                                           |

Deliberately absent: `Subject`, `HtmlBody`, `TextBody`. Those come from the tenant's template, and a body written here would be text this package has no authority over. The test asserts the key set exactly, so a new field cannot arrive quietly.

**Response reading.** `ErrorCode` is the discriminator, not the HTTP status: Postmark answers a refusal in the same schema as a success, so a 200 does not mean accepted and a 401 does not mean the message was refused. Reading it in that order is why a 200 carrying `ErrorCode: 403` is a rejection.

- `accepted` only when HTTP status is **200**, `ErrorCode === 0`, **and** `MessageID` passes `isProviderMessageId` from `@archava/act-email`. A success-shaped body attached to HTTP 404/500/503 or another non-200 status is `unknown`; a 200 with no usable id is `unknown / mail_provider_receipt_absent`. The id is never re-derived or invented.
- `rejected`, keyed by the documented `ErrorCode`: 10, 300, 402, 403, 406, 410, 411, 412, 413, 422, 1101, 1105, 1235, 1236, 1480 → `mail_provider_rejected_*`, `mail_account_not_approved`, `mail_provider_template_unknown`, `mail_provider_stream_unknown`, `mail_provider_stream_unsupported`. Each carries the documentation's own wording as a source comment.
- `rejected`, keyed by HTTP status only when the body carries no usable code: 401, 413, 415, 422, 429 → credential / request / rate-limited.
- `unknown` for a timeout (`mail_provider_did_not_answer`), an unreachable transport (`mail_provider_unreachable`), a non-JSON body (`mail_provider_reply_unreadable`), a status this adapter will not interpret (404/500/503 → `mail_provider_reply_unrecognised`), and a documented non-refusal code such as 100 "offline for maintenance" or 101. The API overview documents 500 as "an issue with Postmark's servers processing your request" and 503 as "planned service outages"; neither is a statement about whether this message was taken, so neither becomes a refusal.
- A code or status the adapter cannot name is never guessed at. 413 is deliberately in **both** maps with different meanings (HTTP: over the 10 MB size limit; code: account not approved to send), which is why the two maps are separate.

**Timeout.** 15 s, the adapter's own bound, because Postmark documents none for this endpoint. The abort signal is fired _and_ the call is raced, so a transport that ignores its signal is still bounded. Long enough not to discard a slow-but-successful send as a timeout; short enough not to pin a turn on a hung socket.

**No retry, ever.** One `transport.post` per `send`, whatever the answer was — refusal, silence, 500, empty body. `EmailOutboxBoundary` owns at-most-once; a retry here would be a second message into a real mailbox.

**Idempotency key.** Postmark documents **no** idempotency-key field anywhere in its API, so there is nowhere honest to put one. The upstream raw key is transformed — `HMAC-SHA256` over a structured, domain-separated tuple of tenant ID and key with an injected ≥32-byte secret, base64url, 43 characters — before it reaches any provider field, and it travels as `Metadata.archava_attempt`. Identical raw keys in different tenants produce different labels. This is a searchable label, not a deduplication promise the provider makes; the at-most-once guarantee stays with the attempt store. The label is stable across processes for the same tenant, key, and secret.

**Status lookup.** Postmark's Messages API supports an outbound search filtered by one metadata field, but this package has **not implemented or verified** a tenant-bound positive reconciliation through it. A search miss is never proof that a message was not sent, because visibility, pagination, and retention leave that question open. `PostmarkStatusPort` therefore answers `unknown / status_not_available` always and never `rejected`.

### Credential and privacy behaviour

- The server token is a **constructor argument only**. The package reads no `process.env`, so a bundle that somehow reached these modules would find no credential to leak; constructing a `PostmarkEmailGateway` with a blank token throws rather than attempting a 401.
- The token appears in exactly one place: the `x-postmark-server-token` header. One test asserts the request body does not contain it.
- Transport failures carry one fixed message. A native network error is dropped rather than quoted, so no URL, proxy host, or token-bearing header dump reaches a reason string, a log line, or the audit trail.
- The raw upstream idempotency key never reaches the wire, a provider field, or a `console` call; it is keyed and one-way before use. A test asserts the request body does not contain it and that the label matches a 43-character base64url opaque value.
- `PostmarkStatusPort` is credential-free by construction and holds nothing a lookup carried: `Object.keys(port)` is exactly `['statusPortId']` and its JSON carries no attempt key.
- Provider prose is never quoted back. Every reason string is a machine code from this package or from `packages/act-email`.

### Not verified — live checks still outstanding

These are the honest gaps. None is asserted anywhere in the code:

1. **A real send.** No credential exists, so the exact request shape has only been checked against the documented schema and a recorder, never against a server. First live send should confirm `From` is accepted by the target server's confirmed Sender Signature and that a `MessageID` comes back with `ErrorCode: 0`.
2. **Metadata limits.** The documentation does not state a maximum key length, value length, or count for `Metadata`. `archava_attempt` with a 43-character base64url value is well within anything plausible, but the limit is unconfirmed — if a deployment needs to be sure, it must be read off the live account.
3. **Rate limits.** The overview documents 10,000 messages per server per minute and a 500-message batch cap; this adapter sends one message per request and exercises neither. 429 maps to `rejected / mail_provider_rate_limited`, but the actual observed behaviour of a throttled single-message send is unverified.
4. **Reply-search correlation.** A metadata-filtered outbound search is documented, but no such search has been performed and no positive-only recovery has been implemented. A search miss cannot authorize a second send — see `PostmarkStatusPort`.
5. **Message stream names.** `outbound` is the documented default and `broadcast` is wired as an option; a deployment using custom streams must confirm the name it passes actually exists, or code 1235 (`mail_provider_stream_unknown`) is what it will read back.

### Integration notes for whoever wires this up

- Construct once per process with the token from a secret store: `new PostmarkEmailGateway({ serverToken, attemptLabelKey })`. `attemptLabelKey` may be the key the outbox already uses, or a distinct one; it must be stable for as long as any attempt can replay, or the label stops being matchable.
- The gateway is stateless apart from the credential and the key, so callers may share one instance and interleave freely.
- `PostmarkStatusPort({ deployment: 'eu-west' })` tags the audit-trail id; nothing else about it changes.

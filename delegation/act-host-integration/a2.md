### Authority proof

The claim this package makes is narrow and structural: a browser can contribute an utterance, one action id, the inputs it typed, and a challenge it was handed — and nothing else reaches `runTurn`. Each half of that is enforced by construction rather than by checking, and each is pinned by a test that fails if the construction moves.

**The envelope has three visitor-owned fields.** `SERVER_OWNED_ENVELOPE_FIELDS` in `src/envelope.ts` lists 38 known server-owned names. `readVisitorEnvelope` returns only `{utterance, action, confirmation?}`. A known forbidden field is recorded in `dropped` by its safe name; an unknown name becomes `unrecognized_field`, because a malicious object key can itself contain sensitive data. Tests enumerate every known server-owned name, reject an overlong action id, reject incomplete confirmation, and verify that an unknown key containing a card-like string never enters the reading or audit marker.

**The challenge is bound before it exists, and to facts the visitor never named.** `review` reads the envelope, asserts the graph's tenant is the host's own constructor tenant (`assertTenant`, so an envelope naming another tenant changes nothing), resolves the action through the registry, runs the existing `ActionPolicy` gate, then `validateActionInputs` — and only an action the gate actually wants confirmed gets a challenge minted. An action the gate would allow outright is refused with no challenge; an action needing a person is refused with `visitor_human_approval_required`; an action the registry does not know, an input the contract does not name, and an entity no authoritative resolver answers for are all refused before the challenge service is called. The challenge carries the server-owned tenant, session, action id, and the **digest of exactly the validated inputs**, so a second candidate with the same action id and changed inputs mints a _different_ challenge — the test asserting that is the same test that proves the store never sees an input.

**The presentation is looked up by the challenge the visitor was handed, never by the action id they typed.** `present` resolves the attempt through `attempts.findByChallenge(challengeId)` and then re-runs `validateActionInputs` against the server-owned action contract, so the payload that reaches `runTurn` is the one the server validated, not the one the envelope last carried. `confirmations.verify` receives those parsed inputs and makes one store consume call. The host now checks that the loaded attempt belongs to its server-owned tenant and session, and that an executor exists, before consuming the challenge. Unknown, cross-session, changed, replayed and expired challenges never reach `runTurn`.

**`occurredAt` is read back, not derived.** The attempt identity (`tenantId`, `sessionId`, `actionId`, the input digest) is looked up in the ledger _before_ deciding the timestamp; if the row exists, its `occurredAt` is used verbatim, and reissued challenges update the record while retaining its first `occurredAt`. This is the one line the whole module exists for, and `describe('ActHost.occurredAt')` asserts a retry after a re-issue, a timeout long enough to expire the challenge, and a re-ask from the same visitor all keep the original instant and therefore the original idempotency key — while a _different_ payload on the same action id produces a different key. `test/host.test.ts` asserts both halves in one place: two presentations of two different challenges for the same attempt reach the executor with identical action and inputs, and the set of idempotency keys the executor was handed has size 1.

**Nothing sensitive lands anywhere a log or a browser could read it.** Refusals are drawn from a closed list of 12 `ACT_HOST_REFUSAL_CODES` and never carry a token, a raw input, an entity id or an idempotency key — an envelope refusal names the _reason code_ (`not_an_object`, `utterance_invalid`, `action_invalid`, `confirmation_invalid`) and nothing else. `ActHost.refusals` asserts exactly those negatives: `carries no token in the refusal it throws`, and `keeps a raw form value out of every attempt record it writes`. The attempt record holds the digest, the challenge id and the instant, and deliberately not the inputs, the token, the utterance, the policy verdict or the executor's output, which is what makes an attempt record safe to log. The test names assert the other half: forged capability and confirmation fields and extra browser candidates are dropped; the valid, service-confirmed candidate can still execute. None of the dropped candidates reaches the executor.

### Safety proof

**`runTurn` is the final gate, not the first one.** The `ActionPolicy`, the validation and the entity-resolution checks are preserved inside `runTurn` by composing the host through it — the challenge only decides that a request may be _considered_, and `runTurn` still decides what may _happen_. The gate is consulted at two distances, and the second one is the one that counts. `review` consults it before anything is minted, so an action whose gate wants an operator rather than a visitor never gets a challenge at all: `it('refuses to mint a confirmation where the gate wants a person, not a visitor')` wires the real policy against `admin.config.update`, asks the host to mint, and gets `visitor_human_approval_required` back with `confirmation.store.issues === 0` — there is no token to present, so there is nothing for `runTurn` to refuse. But nothing about the challenge is trusted to have been true at the time it was minted, and `present` composes through `runTurn` with the server's own policy, validator and resolver, so a gate that denies on the way through stops the action after the challenge was spent and before any provider is called. The structural evidence for that second gate being live rather than assumed is that it is the _same_ `ActionPolicy` instance the review path uses — and `it('refuses a page that does not offer the action, before it will ask about inputs')` is what shows that instance deciding, not a copy of one.

**No provider write on any rejection.** Every rejected path — bad envelope shape, wrong tenant or session, unknown action, missing or unknown entity, extra input field, action the gate allows outright, expired challenge, replayed challenge, mismatched action, changed inputs, absent executor, **a store that will not take a challenge at mint time, and a store that will not spend one at present time** — is asserted to reach the executor zero times. `test/fakes.ts` records the executor calls, and each such test asserts `executor.calls` is empty alongside the refusal. The two outage cases are the ones worth naming out loud, because they are the failure a deployment will actually hit: `it('refuses to hand out a token the store would not keep')` drives both an unreachable store and a conflicting insert, and `it('refuses rather than executes when the store cannot spend the challenge')` cuts the store out _after_ the challenge was minted — and asserts not only that the executor was never reached, but that the challenge is still `pending` in the store, so a retry against a store that answers is still a retry and not a dead receipt.

**An unknown provider outcome is never a success claim.** `ActionExecutionResult` in `packages/assistant/src/execution.ts` is a closed two-member union: `succeeded` with an output or `failed` with a machine-readable code. `uncertainExecutor` reports `failed` with `errorCode: 'provider_outcome_unknown'` and `retryable: true`. The host asks it once, projects `failed` into `ActHostPresentation`, and uses deterministic failure text. The internal `runTurn` timestamp stays server-side; the attempt ledger and executor request demonstrate that retries use the same idempotency key.

**No shared seam was weakened.** `packages/assistant`, `packages/acl`, `packages/act`, and `packages/act-confirmation` remain unchanged. `ActionExecutionRequest` still carries `{tenantId, sessionId, action, inputs, idempotencyKey}` internally. `ActHost.present` returns only a safe projection; the attempt ledger is the server-side source for retry time.

### Remaining host and transport limits

1. **No transport.** `ActHost.present` and `ActHost.review` are TypeScript APIs, not routes. There is no HTTP handler, no session cookie, no CORS posture, no rate limit and no browser bundle — deliberately, per the charter. A deployment must put this behind a server-only route that derives tenant and session from its own session store and never from the request body.
2. **The attempt ledger is required, but durable storage is not supplied here.** The constructor refuses a missing `ActHostAttemptLedger`. `InMemoryActHostAttemptLedger` remains an explicit test/reference implementation and loses records on restart. A deployment must inject a durable implementation with atomic canonical-open semantics before relying on same-attempt retry identity. The current `find` then `save` port sequence is not atomic, so concurrent reviews against a naive shared ledger could record different `occurredAt` values. This is an unresolved production blocker.
3. **The confirmation store must also be durable.** `ConfirmationChallengeStore` is a port; the tests use a local atomic double because `packages/act-confirmation` ships no durable in-memory store. A deployment needs a1's `PostgresChallengeStore` (or equivalent) wired in, and challenge records must outlive `expires_at` by the retention contract a1 documented. Both store failure modes a deployment will meet — an unreachable store and an insert it refuses — are driven against that double in the tests, so the host's behaviour under a store that stops answering mid-flow is a tested behaviour and not an assumed one.
4. **No PMS, no mail provider.** Nothing here books, sends, or charges. The `EntityResolver` and provider ports are doubled in tests with fakes that record, never act.
5. **The browser remains offline.** No UI exercises this flow; the human side of every confirmation is unexercised beyond the challenge token's round trip through a fake.
6. **Clock and concurrency are deployment concerns.** The confirmation service's clock determines a challenge's issue time. The host's injected clock is used for a read-only probe. Shared hosts need a durable, atomic attempt ledger to select one canonical `occurredAt` under concurrent reviews.
7. **`review` cannot mint a challenge for an action the gate wants to ignore.** That is correct behaviour, not a gap, but it means a wildcard or catch-all policy entry that allows an action without confirmation will be refused here rather than confirmed — a deployment authoring such a rule should confirm it wants a challenge anyway.

### Lead audit amendments

The initial command log above records the a2 handoff. After the lead audit, focused tests passed with **48 tests in 2 files**. The challenge and bound action use parsed inputs from `validateActionInputs`, including normalization of nested objects. A valid challenge from another session on a shared store is refused before consume. An absent executor leaves the challenge pending. The in-memory challenge store in focused tests wraps the real `ConfirmationService`; it does not prove PostgreSQL behavior.

Retry identity currently has no terminal/new-intent discriminator: a genuinely new request with the same tenant, session, action and parsed inputs reuses the old `occurredAt` and idempotency key indefinitely. The ledger port also lacks an atomic open operation across concurrent hosts. Both require a durable attempt lifecycle design before production use. The host has no HTTP transport, authenticated session source, live booking provider, or browser confirmation UI.

`ActHost.present` now returns `ActHostPresentation`, a narrow deterministic result containing only action ID, execution state, safe error code when applicable, and user-facing text. It never returns the internal `TurnOutcome`, action inputs, idempotency key, model components or citations, structured truth, or events. Tests serialize a secret-bearing result and assert the input, challenge token, and key are absent. Success text comes from a verified executor success; non-success text makes no completion claim. The internal `runTurn` result remains server-only.

The lead audit also found that `validateActionInputs` can quote an unresolved entity value and an unknown input name. `ActHostRefusal.fields` now projects validation failures to a generic public reason instead of forwarding those strings. Unknown top-level envelope keys likewise become `unrecognized_field` in the audit marker; only known server-owned names are reported verbatim. Focused host tests pass **49/49** after these changes.

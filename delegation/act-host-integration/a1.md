### SQL safety proof

**No caller value is ever SQL text.** `statements.ts` is the only place a statement is built, and it takes no caller string into the SQL: it interpolates `CHALLENGE_COLUMNS` (a frozen `as const` array in the same file) and nothing else. Every identity, digest and instant becomes a bound `$n`.

What `test/statements.test.ts` verifies is the **shape**: the exact SQL text of all three statements, the exact parameter array in order, that `'pending'` and `'consumed'` are SQL text rather than caller data, that no `now()` appears anywhere, that `lookup` carries no tenant or session predicate, and that the placeholder accounting is exact — `issue` uses `$1`–`$8`, `consume` uses `$1`–`$9`, `lookup` uses `$1`; eighteen placeholder occurrences in total, each appearing exactly once in its statement with exactly one matching parameter. (`consume`'s `$2`, `$8`, and `$9` are distinct placeholders that carry the same caller instant.)

One gap, stated plainly rather than papered over: **no test in this package feeds a value shaped like an injection attempt.** Every fixture is a benign identifier — `challenge-42`, `'a'.repeat(64)` — and nothing anywhere in `test/` contains a quote, a semicolon, `--`, or a `$n`. The reason that gap is not a hazard is structural, not tested: a caller string can only ever become a `$n` parameter, because `statements.ts` builds SQL from a frozen column array and never concatenates a caller value into it. But "impossible by construction" and "demonstrated against a hostile fixture" are different claims, and only the first is backed here. A reviewer who wants the second should add those fixtures.

**The container seam.** `@archava/act-storage`'s `SqlClient` is used unchanged; nothing was added to it and no driver was added anywhere. A `SqlClient` is injected into `PostgresChallengeStore`, so the store cannot reach a database except through an interface it does not implement.

**`scripts/postgres-shell.ts` is not part of that proof and is not asked to be.** It binds parameters by substituting literals into a string, because the only thing it serves is `psql` over argv. That is safe here for one narrow reason: every value it substitutes is either a constant in this package's own fixtures or an identity handed over by the verifier that spawned it. It refuses anything that is not a finite safe-integer number or a string, so a value it cannot render exactly raises instead of being approximated. It is never reachable from `src/`, from `test/`, or from a caller of the store.

**`issue` — one row for one id.** A single `INSERT ... ON CONFLICT (id) DO NOTHING RETURNING id`. The conflict target is named, so a uniqueness violation from any _other_ constraint raises rather than being swallowed by a targetless `DO NOTHING`. Rows skipped by `ON CONFLICT DO NOTHING` never appear in `RETURNING`, so zero rows is an unambiguous "the id is taken", and the loser gets a refusal rather than an error.

**`consume` — the database decides, in the same step that spends.** A single conditional `UPDATE ... SET state = 'consumed', consumed_at = $2 WHERE id = $1 AND tenant_id = $3 AND session_id = $4 AND action_id = $5 AND token_digest = $6 AND binding_digest = $7 AND state = 'pending' AND $8 >= issued_at AND $9 < expires_at RETURNING <the ten columns>`. There is no read followed by a write, so there is no window for two callers to both complete. `$2`, `$8`, and `$9` are the same caller-supplied instant bound three times on purpose, so the stamp and both window comparisons are on one timeline. The database's `now()` is never used: the service neither controls it nor observes it. The window comparison uses integer epoch milliseconds in `bigint`, not `timestamptz`, so timezone and binary-float rounding do not enter it. The store also validates that a returned row describes the exact presented identity and a consumed state stamped at the supplied instant.

**Zero rows is classified by a read, and the read is deliberately unscoped.** `lookup` reads by id and nothing else. Scoping it by tenant, session or digests would turn "wrong tenant" into "no such challenge", which is the one distinction this package must be able to make; the comparison against what was presented happens in this package over the row `lookup` returns.

The verdict is one of `spent`, `mismatch`, `already_consumed`, `expired`, `not_found`, or `unavailable`, and its **order is a security property rather than a tidiness one**: `classify` asks whether the presentation matches before it asks anything about the row's state. That is what stops a cross-tenant replay from being handed `already_consumed` — such a caller is told it matched nothing, not told that somebody else already spent the challenge. `expired` is likewise _computed_, not read: it comes from the row's `expires_at` against the caller's supplied instant. A matching row presented before issuance or a pending, matching in-window row that the predicate somehow declined has no matching port verdict, so it is reported as `unavailable` rather than smoothed into a friendlier answer.

**Fail closed.** A database error, a row that cannot be decoded without guessing, and an uncertain write are all refusals rather than guesses: an error is thrown, not swallowed; a malformed row is a refusal; `lookup` and `consume` never invent a verdict from an absent row.

**What the migration's constraints add.** `state` is limited to the port's four states; `consumed_at IS NOT NULL` is tied to `state = 'consumed'` in both directions; `expires_at > issued_at`. The primary key is on `id` alone and is `NOT DEFERRABLE`, which is what makes `ON CONFLICT (id)` a legal arbiter.

### Official documentation verified

Fetched during this work, quoted verbatim.

- **`INSERT ... ON CONFLICT`**, <https://www.postgresql.org/docs/current/sql-insert.html> — "In all cases, only `NOT DEFERRABLE` constraints and unique indexes are supported as arbiters." Also: a `conflict_target` is optional for `DO NOTHING` but mandatory for `DO UPDATE`, "`ON CONFLICT DO NOTHING` simply avoids inserting a row as its alternative action", and rows skipped by `DO NOTHING` are not returned by `RETURNING`. This is the basis for naming `(id)` rather than writing a targetless `DO NOTHING`.
- **`UPDATE`**, <https://www.postgresql.org/docs/current/sql-update.html> — the `WHERE` clause restricts which rows are updated, and `RETURNING` is "computed over the row(s) actually updated"; only rows that reached the version the predicate matched are returned.
- **Read Committed concurrency**, <https://www.postgresql.org/docs/current/transaction-iso.html> — "The search condition of the command (the `WHERE` clause) is re-evaluated to see if the updated version of the row still matches the search condition. If so, the second updater proceeds with its operation using the updated version of the row." This is the documented reason two processes cannot both consume one challenge: once the first commits `state = 'consumed'`, the second's `AND state = 'pending'` no longer matches on the re-evaluated row.
- **`psql` error handling**, <https://www.postgresql.org/docs/current/app-psql.html> — `ON_ERROR_STOP=on` exits nonzero when a script encounters an SQL error; without it, command processing continues by default.
- **Connection settings**, <https://www.postgresql.org/docs/current/runtime-config-connection.html> — an empty `listen_addresses` disables TCP interfaces, leaving the verifier's private Unix socket available.

Earlier rounds of this work also verified explicit-locking, MVCC, DDL constraints, multiple-rows-unknown, and `CREATE TABLE` pages from the same documentation set. Nothing in this package relies on an undocumented behaviour, and no behaviour here is documented only by this Result.

### What the offline tests cannot prove

68 tests in 3 files pass with no database. They are honest about their limits:

- **They cannot prove PostgreSQL agrees.** Every one of them runs against a recording `SqlClient` in this repository. They assert what the store _sends_ and what it _concludes_ — parameter order, predicate contents, that a zero-row transition is classified rather than guessed, that a thrown error propagates as a refusal. Whether a real server accepts the SQL, honours `ON CONFLICT (id)`, or re-evaluates the predicate under Read Committed is proved only by `verify:sql`, which needs a local PostgreSQL and does not run in ordinary CI.
- **They cannot create a real race.** The recursive and concurrent cases are in-memory races against a fake client, serialised by the test runner. They prove the store never _invents_ a second transition, which is not the same as proving two processes cannot both complete a transition. Only the child-process races in `verify:sql` speak to that.
- **They cannot prove durability across a restart.** Only `a spent challenge survives the server being restarted` does, and only in `verify:sql`.
- **They cannot prove the constraint exists.** `the server, not the store, refuses a duplicate id` needs the real server; the offline suite asserts only that the store does not raise on a collision.
- **They do not exercise injection-shaped input.** Every fixture in `test/` is a benign identifier; nothing contains a quote, a semicolon, `--`, or a `$n`. The SQL-injection resistance in this package rests on `statements.ts` never concatenating a caller value into the SQL, which is a construction property, not a tested one. See the gap stated under SQL safety proof above.
- **`scripts/postgres-shell.ts` is deliberately outside the proof**, and is not claimed to be safe against hostile input (see the seam paragraph above).

So: `pnpm test` green is evidence about this code's logic, not about production behaviour under PostgreSQL. The two are kept apart on purpose, and neither stands in for the other.

### What the table stores, and for how long

`confirmation_challenges` stores exactly: `id`, `tenant_id`, `session_id`, `action_id` (opaque identifiers, no PII), `token_digest` and `binding_digest` (HMAC-SHA-256 hex from `@archava/act-confirmation`, so a dump is not a usable confirmation), `state`, and three epoch-millisecond instants `issued_at`, `expires_at`, `consumed_at`. It stores no part of any token or key, no browser identifier, no IP, no user agent, no mail address, no action payload, and no provider payload. The migration states this as a rule for future columns: a column that names a person, a message body or a credential belongs somewhere else.

Retention is a diagnostics commitment, not a safety one, and this package performs no deletion: every path that finds no row answers "unknown" and the service refuses it, so a deleted challenge never creates a double confirmation. A deployment should keep **consumed rows at least as long as an operator wants the difference between "already consumed" and "no such challenge"** — past that, a replay becomes indistinguishable from a forged id — keep **pending rows past `expires_at` plus the clock skew between the issuing and enforcing processes**, and **never delete a row while it is pending**, because "expired" is a verdict this store reports, not a state a sweeper may assert on the row's behalf.

### Remaining deployment requirements

1. **A driver, at the composition site.** `PostgresChallengeStore` accepts a `SqlClient`, and none ships here by design. The host that composes it must inject one (a `pg`-based client is the obvious choice); the README's ban on adding a driver to _this_ package is not a ban on adding one at the wiring site.
2. **Apply the migration.** `migrations/001_confirmation_challenges.sql` must be applied to the deployment database. It is `IF NOT EXISTS` throughout and adds no data.
3. **Clock agreement on the presentation instant.** The store compares the caller's instant, never the server's. The caller and the web tier must share a clock source, or an expiry will mean slightly different things to each.
4. **A sweep is a policy decision, not a schema one.** Nothing deletes rows; if a deployment wants one, it is a separate change and must respect the retention contract above.
5. **The verifier is optional tooling.** `verify:sql` is not run by CI and is not a runtime dependency of anything; it needs local `initdb`/`psql`. The disposable PostgreSQL instance uses a private Unix socket and no TCP listener.

### The seam

`composeTenantActExecutor(configuration)` returns a `TenantActExecutor`. It is the only production entry point, and it is impossible to construct one accidentally with bare gateways: the factory itself builds `BookingReplayBoundary` and `EmailOutboxBoundary`, and the outputs of those two constructors are the only gateway objects the executors are ever handed. There is no parameter through which a caller can supply an unwrapped gateway, because `TenantActConfiguration` names a `BookingGateway`/`EmailGateway` — an _argument to a boundary_, never to an executor.

The configuration it refuses to accept incomplete, with a machine-readable `ActCompositionFault` and a message that never names the tenant, the provider or the port implementation:

- a blank or absent `tenantId` → `act_composition_tenant_missing`
- a fingerprint key that is a string, or shorter than 32 bytes → `act_composition_fingerprint_key_not_bytes` / `..._too_short`
- each missing or malformed port, one reason per seam: `..._booking_gateway_identity_missing`, `..._booking_gateway_unusable`, `..._booking_store_identity_missing`, `..._booking_store_unusable`, `..._reconciler_identity_missing`, `..._reconciler_unusable`, `..._email_gateway_unusable`, `..._email_store_identity_missing`, `..._email_store_unusable`, `..._status_port_identity_missing`, `..._status_port_unusable`, `..._template_resolver_unusable`

The checks are structural (`isPlainObject`, non-blank identity strings, callable methods) rather than type-trusted, because the caller is a request handler, a config loader or a test — three things that have each, at some point, handed a placeholder where a port was meant to go. A refused construction returns no partially wired executor at all, since a partially wired executor is one that can be talked into reporting a side effect it cannot make.

### Authority proof

The factory authorizes nothing. It reads no policy, no confirmation, no `DecisionProvider` score and no capability tier; the frozen path is unchanged:

`ActionPolicy → verified user confirmation → §9 input validation → trusted entity resolver → ActionExecutor`

and the seam sits below all four. `composition.test.ts` pins the resulting invariants:

- `handles(action, tenantId)` answers whether this executor may act _as its own business_, and the doc comment says explicitly that it is not a policy decision and never has been.
- Tenant mismatch and non-dispatched actions are refused by the seam itself as `{status:'failed', errorCode:'act_executor_tenant_mismatch'|'act_action_not_dispatched', retryable:false}` — a declined request addressed to someone else's deployment, not a denial of an action.
- `workflow.test.ts` proves the seam cannot restore a capability it does not own: Assist tier and unconfirmed Act both still refuse with the composition in place, because capability and role are the client's own.
- It cannot override a failed entity resolution either — an unresolvable slot is recorded as `{policy:'denied', execution:'not_attempted'}`, never `'failed'`, because nothing was attempted.
- `never reports an unknown outcome as a booking, and never retries it` — an `unknown` gateway outcome is a failed, non-retryable result whose rendering contains no booking reference, and the record's terminal state is `unknown`. Exactly one gateway call is made; the reconciler's "not found" is not a booking either.
- `succeeds on provider acceptance, and never claims delivery` — a `providerMessageId` is reported as acceptance, and the rendered output contains neither `delivered` nor the recipient address.
- `sends only an approved template` — the resolver is tenant-bound and re-checked with `isOwnedTemplate`, so a template that is not this tenant's own, approved record resolves to `null` and no send happens.
- Model-written email body is rejected: the `body`-carrying inputs case is in the blocked list, since body text is never trusted input.
- `refuses a same-key payload change rather than re-issuing it` — the boundary refuses a second reservation for a changed payload under a claimed key.
- `replays the same key and payload without a second port call` — a repeat is answered from the store, and `bookingClaims` shows two claims, one gateway call.

Browser-provided values never become trusted configuration: `TenantActConfiguration` is a server-side TypeScript interface with no `unknown`-typed fields for provider names, keys, senders, prices, availability or confirmation flags. Nothing on the type can be populated from a request body; provider names, keys and senders enter only through the ports a deployment constructs in its own server process.

### Tenant-safety proof

The binding is the seam's own and is separate from authorization. `readTenantId` trims so a config file's trailing newline does not silently create a second tenant scope, and every port call carries that tenant id:

- `carries its tenant onto every port call, for both actions` — booking, email and template resolution all see `TENANT`.
- `refuses a request addressed to another tenant without calling any port` — no gateway call, no `claim` at all.
- `will not resolve a template for a tenant it was not composed for` — `templateCalls` is empty, so a cross-tenant id cannot even be looked up, let alone pick up another tenant's sender.
- `refuses a turn that was built for a tenant it was never configured for` — through the real `runTurn`, where the other tenant's config, graph and resolver are all consistent and only the executor is this one. It refuses, and no booking is recorded.
- `reports its own tenant and nothing else` — `handles` is false for `OTHER_TENANT` and for an action this package does not dispatch.

### Remaining production gaps

Not claimed by this work, and deliberately out of its reach:

1. **No production store.** Only the `BookingAttemptStore` / `EmailAttemptStore` interfaces are used. The in-memory `claim` in `test/fakes.ts` is deliberately _not_ atomic across processes, which is exactly why both port contracts document that a production deployment must supply durable ones. a1's PostgreSQL adapter is the intended implementation; importing it here would have coupled the two and was avoided on purpose.
2. **No selected PMS or mail provider.** The gateways are ports. Nothing here chooses a vendor, and no provider credential, template or key name appears in any test.
3. **No host for the keys.** `fingerprintKeys.booking` / `.email` must be 32+ bytes of server-only entropy, stable while records live, and must never reach a browser bundle. Producing, storing and rotating them is host configuration this factory only validates.
4. **No live verification.** A confirmed fake booking is not a booking and an accepted fake email is not a delivery; `fakes.ts` says so in its header. A real PMS reservation, a real provider send, and a Jev evaluation remain outstanding.
5. **No call-site yet.** `composeTenantActExecutor` is meant to be called once per tenant per process at startup from server configuration; no such call site exists in this round, so nothing wires the composition into a running server.

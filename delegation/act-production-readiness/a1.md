## Result

Implemented and reconciled by the lead audit in `packages/act-storage/**`. The
original a1 Result was still pending when the lead began the audit; the package
files were already present and were preserved. The audit found one privacy bug:
the assistant's raw idempotency key serializes canonical action inputs, but the
initial adapter persisted it directly. The adapter now persists only a
tenant/action-bound HMAC of that key, while returning the original key through
the existing public store ports.

Files: `migrations/001_act_attempts.sql`, `src/{booking-store,core,email-store,index,row,sql,statements,storage-key}.ts`, `test/{booking-store,email-store,recording-sql-client,row,statements,storage-key}.ts`, `scripts/verify-against-postgres.ts`, `package.json`, `tsconfig.json`.

SQL invariants: the primary key `(tenant_id, action_kind, idempotency_key)`
arbitrates an `INSERT ... ON CONFLICT DO NOTHING RETURNING` claim. A conditional
`UPDATE ... WHERE state = $4 RETURNING` settles only a matching state. All
identity values are parameters, and `idempotency_key` receives a 64-character
HMAC-SHA256 digest, never the raw pipeline key. A lost claim reads the winner;
a failed database operation or malformed row does not become a successful
claim or settlement. The table never deletes a row. Retention must exceed the
entire retry lifetime.

Current official PostgreSQL references checked: [INSERT / ON CONFLICT / RETURNING](https://www.postgresql.org/docs/current/sql-insert.html), [UPDATE / RETURNING](https://www.postgresql.org/docs/current/sql-update.html), and [transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html). The optional `verify:sql` command applied the migration to a throwaway local PostgreSQL cluster and passed 14 schema/statement invariants plus two-process claim and settlement races and a stale read/write race. This verifies PostgreSQL behavior on this machine; the recording fake alone does not prove it.

Production wiring still requires a driver-backed `SqlClient`, applying the
migration in the target database, and one securely provisioned 32-byte-or-longer
storage HMAC secret that stays identical across processes and restarts. Secret
rotation requires migrating old attempt identities before accepting new claims;
otherwise old attempts appear unclaimed and could be repeated. This package
does not implement a PMS, mail transport, deployment host, or live provider
verification. No credentials are stored here. No new runtime dependency was
added; HMAC uses Node's built-in `crypto` module.

### Why the boundary is a `BookingGateway`

The boundary implements `BookingGateway`, so it is passed to the existing `BookingActionExecutor` as its `gateway` option. Nothing else had to change: an executor holding a raw gateway holds a wrapped one, and the executor cannot tell them apart. The authority chain is untouched — ActionPolicy → confirmation → validation → trusted entity resolver → ActionExecutor → boundary → authoritative gateway. This package still authorises nothing and confirms nothing.

### The contract, in five statements

1. **One tenant-scoped key issues at most one reservation.** `claim` asserts ownership atomically before any write. A key that is already owned is never issued again — not concurrently, not after a restart, not on a second button press.
2. **Same key and same payload replays.** The second caller gets the reference the authoritative system issued, served from the record with no write anywhere.
3. **Same key and different payload is a conflict.** The call is refused with `idempotency_key_conflict` and `retryable: false`. The check lives in the boundary, not only in the store, so a store that answered loosely cannot turn a payload change into a replay. The fingerprint is `JSON.stringify([tenantId, slotId, customerRef, notes ?? null])`, with the tenant included so a store that ignored the tenant scope is still caught here.
4. **An unknown outcome is never laundered into a success.** An unknown is recorded as unknown and reported as `booking_outcome_unknown` with `retryable: false`. It never becomes a confirmation and it never authorises a second write.
5. **The only permitted second look is an authoritative reconciliation, and it is a read.** `BookingReconciliationPort.reconcile(lookup)` receives the tenant, key and fingerprint and nothing else — deliberately no slot, no customer reference — so a lookup port cannot be handed the means to make a second reservation. If the system cannot look the attempt up, the boundary answers unknown and writes nothing.

State is `in_flight → confirmed | rejected | unknown`. An unsettled record looks in-flight to the next process, so every branch settles, including `settle()` failures after a confirmed write — there the reference is kept, because withdrawing it would tell a visitor nothing was booked while a booking stands, and the record is reconciled rather than re-issued.

Confirmed success passes the existing `isConfirmedBooking()` guard on both paths. A `confirmed` reply with no usable reference is not a confirmation, wherever it came from: from the gateway it is `booking_reply_unrecognised`, from a stored record it is `stored_reference_unusable`. Neither reports a booking.

An unreachable system is checked before a key is claimed, so an outage does not leave a caller holding a record that nothing ever made. A throw from `health` is absorbed. Provider prose is flattened to a machine code against `/^[a-z][a-z0-9_]{0,39}$/`, defaulting to `booking_outcome_unexplained`, so neither a tenant's data nor a provider's own words reach public output.

### Remaining external gaps

These are not things this package can close from inside itself.

1. **No PMS was selected.** No provider is chosen and no PMS API surface is named or invented anywhere in this change. Every provider interaction is behind `BookingGateway` and `BookingReconciliationPort`, and neither port has a real implementation. Selecting one requires a real tenant with a real PMS and that vendor's verified official documentation, neither of which exists here.
2. **The attempt store is a port with no durable implementation.** `attemptStore()` in the tests is an in-memory `Map`. It is a test double and the suite says so. A production store must make `claim` atomic across processes — the usual answer is a unique index on `(tenantId, idempotencyKey)` with an insert-or-nothing, and it is the deployment's to make. This package's guarantee of one reservation per key extends only as far as that store's uniqueness does.
3. **No cross-process atomicity is proved.** The fake's `claim` contains no `await`, so its read-modify-write completes before anything else in the process can interleave. That demonstrates single-process atomicity and nothing more; the test comments state this rather than implying otherwise.
4. **The reconciliation port is a read with no reader.** No tenant-credentialed lookup against a real system exists. `BookingAttemptRecord` stores the fingerprint, not the payload, so even the reconciler cannot reconstruct a slot or a customer — which is deliberate, but it means a tenant whose PMS cannot look an idempotency effort up by key will stay on unknown forever rather than ever recovering a timed-out attempt.
5. **The boundary is exported but not constructed anywhere.** `packages/act` still builds `BookingActionExecutor` with a bare gateway. Whether the boundary wraps it in production is an infrastructure decision, made below rather than made here.
